# Глубокий анализ проекта и стратегия HTMX-рефакторинга

## 1) Текущая архитектура
- Приложение построено на Django (MVT) с серверным рендерингом шаблонов.
- Домены: управление подключениями к БД, пользователями, группами, аудитом и настройками.
- Основная бизнес-логика сосредоточена во view-функциях в `db_crp/views_*.py`.
- UI построен на полноэкранных переходах между шаблонами (`templates/*`).

## 2) Главные проблемы до миграции
1. **Полные перезагрузки страниц** для большинства сценариев CRUD.
2. **Дублирование шаблонных блоков** (например, блоки сообщений).
3. **Клиентская фильтрация на JS** в списках, что не масштабируется при больших данных.
4. **Слабая композиция интерфейса**: нет единой инфраструктуры частичных обновлений.

## 3) Что изменено в рамках HTMX-перехода
### 3.1 Базовая HTMX-инфраструктура
- Добавлен модуль `db_crp/htmx.py` с унифицированным helper-рендерингом:
  - `is_htmx(request)`
  - `render_htmx(..., partial_template=...)`
- Добавен общий partial для flash-сообщений: `templates/partials/messages.html`.
- В `templates/base.html` добавлено:
  - подключение HTMX,
  - `hx-boost` на уровне `<body>`,
  - централизованная зона обновления `#app-content`.

### 3.2 Переход списков на серверную HTMX-фильтрацию
Переписаны ключевые списки:
- Пользователи: `user_list` + partial `templates/users/_user_list_content.html`.
- Группы: `group_list` + partial `templates/groups/_group_list_content.html`.
- Базы данных: `database_list` + partial `templates/databases/_database_list_content.html`.

Теперь поиск выполняется через `hx-get` c `delay`, а сервер возвращает только нужный фрагмент списка.

## 4) Технический эффект
- Снижена стоимость навигации (частичные обновления вместо full reload).
- Упрощено расширение: любой view можно перевести на partial-ответ через `render_htmx`.
- Улучшена поддерживаемость: сообщения стандартизированы в одном partial.
